# Requirements

Requirements are grouped by the role that must satisfy them: the **finder** (`VSLA-F-*`), the **disclosure
platform** (`VSLA-P-*`) and the **verifier** (`VSLA-V-*`; usually the platform, but anyone may verify). Each
requirement names the lowest level at which it is mandatory. A level is met on a track only when every
requirement at or below that level is met on every pillar.

Implementations SHOULD cite requirement ids in their tests and documentation. The reference verifier's tests
(`tests/test_reference.py`) cite, in their docstrings, F-1, F-2, F-4, F-15, F-16, F-18, F-20, P-3, P-4, P-10, P-11,
P-14, P-16 and V-1 to V-7; qudisclose's tests cite the ids they pin. Not every requirement has a test yet, and this
document does not claim otherwise.

## Finder requirements

### Evidence pillar

| Id | Level | Requirement |
|---|---|---|
| VSLA-F-1 | L1 | The finder MUST produce a statement conforming to [provenance](provenance.md), in a DSSE envelope, signed with the finder's Ed25519 key. Every canonical body in VSLA is RFC 8785 (JCS) JSON. |
| VSLA-F-2 | L1 | `subject` MUST contain the digest of the report (the fields that describe the bug; not contact or credit) and the exact revision of the codebase (git commit, and tree digest when the sandbox was not a git checkout). `reproduction.revision` MUST equal that commit. In the embargoed profile `subject[1].name` is `repo:sha256:<digest of the URL>`, never the URL. |
| VSLA-F-3 | L1 | The MBOM MUST list every model that produced or filtered content on the path to the finding, with role, provider, name, family, version and serving mode. For a model the operator serves itself, the MBOM MUST carry either a digest of the loaded weight bytes or `unmeasured: true`; a digest of the model's *name* is a false statement. Omitting a model that took part voids the statement. |
| VSLA-F-4 | L1 | The transcript MUST be committed as an RFC 6962 Merkle root over ordered leaves, one leaf per model turn and per tool call, each leaf a digest of a canonical JSON body. Leaf 0 MUST be the `measure` leaf; a `verify` leaf MUST record the reproduction's command, exit, classification and output digest, and MUST agree with the `reproduction` section. The leaf count MUST be in the statement. Leaf bodies MAY be omitted and MUST then be retained for the platform's retention period, or sealed to the platform's key. A Merkle root is tamper-evident after commitment; it does not prove the transcript is complete (see [threats](threats.md) T2). |
| VSLA-F-5 | L1 | The reproduction MUST have been executed by code (a test runner, not a model's assertion that it ran). The statement MUST contain the test digest, the exact command (or its digest in the embargoed profile), the expected and observed exit codes, the revision executed against, a digest of the output, and start and end times. On the Finding track `securityFailure` MUST be set by the normative classifier: the runner collected and executed at least one test; at least one test failed by an assertion raised in the test or the code under test; no collection, import, syntax, fixture or timeout error occurred. A substring search over output is not a classifier. The classifier reads the runner's own report, which a hostile test running inside the runner's process can in principle forge; it therefore defends against honest non-security failures (a missing import, a fixture error, a timeout), not against a finder determined to fail on demand, and a platform MUST NOT describe it as more. L1 proves that the test is reproducible, not that the bug is real; the platform's own re-execution and classification (P-4) is what speaks to that. A finder MAY additionally carry a `reference` execution (the same test passing at a stated reference revision or on the patched tree); a platform MAY re-execute it, and the Patch track already requires the differential form. |
| VSLA-F-6 | L1 (Patch) | On the Patch track the statement MUST additionally contain the diff digest, the files touched (or their digest), the computed `scope`, and the results of three executions in a clean checkout: diff application, the reproduction test, and the project's test suite. All three MUST have succeeded. |
| VSLA-F-7 | L1 | The finder MUST treat the codebase, the report and tool outputs as untrusted input (wrap, scan, and execute a proof-of-concept only as a test inside its sandbox, never as a shell command in its own context), and MUST record in the statement any injection it detected. |
| VSLA-F-18 | L2 (Patch) | A Patch L2 claim MUST be `scope: source-only`: the diff touches only source files of the affected component. A change to build scripts, CI, test fixtures, binary or generated files, dependency manifests or release tooling is `scope: mixed` and caps the Patch track at L1 regardless of review. This is where real supply-chain compromises have landed. |

### Identity pillar

| Id | Level | Requirement |
|---|---|---|
| VSLA-F-8 | L1 | The finder MUST have a stable identity: an Ed25519 key pair whose public key is published by the operator and is the one that signs statements. One key per finder; an operator running several finders uses several keys. |
| VSLA-F-9 | L1 | The statement MUST name the operator accountable for the finder and the harness (name, version, digest) that ran it. |
| VSLA-F-19 | L1 | The statement MUST name the basis on which the finder was entitled to test the codebase (`ownership`, a published `program` scope, a written `engagement`, or a `safe-harbour` policy) and a reference to it. VSLA records authorization; it cannot enforce it, and it has no lever over a hunter that never discloses. |
| VSLA-F-10 | L2 | The finder MUST disclose through the authoritative channel the codebase declares (`SECURITY.md`, `security.txt`, registry metadata), and the statement MUST name that channel and the platform's public key. |
| VSLA-F-11 | L2 | The finder MUST include its trust ledger root in the statement, and MUST make the ledger (the countersigned entries for the statement's track, in the order its operator appended them) available to the platform. A summary without the entries is not evidence. The finder MUST keep one ledger per track; every outcome entry names the finder's key or a predecessor in its successor chain; the finder's operator, and nobody else, assigns the order. |
| VSLA-F-12 | L2 | The finder MUST NOT release the finding, a mitigation, or a fix through any non-authoritative channel before the platform's embargo ends. Doing so is recorded in the ledger as `non-authoritative-release` by any platform that observes it. |
| VSLA-F-20 | L1 | A finder key MAY be rotated with a `successor` ledger entry signed by the old and the new key; a verifier follows the chain backwards from the pinned current key, so outcomes earned under the old key count for the new one. An operator MAY revoke a finder key with a `revoke` entry signed under the pinned `operator:` keyid it names. A verifier MUST fail I1 for a statement under a revoked key, or any key in its chain, when the revocation's `at` is not after the statement's evaluation instant `t_eval` (V-7); "dated" means dated by a third party or the verifier, never by the key holder. Both entry kinds are processed by the reference verifier and by qudisclose. |

### Environment pillar

| Id | Level | Requirement |
|---|---|---|
| VSLA-F-13 | L1 | The MBOM MUST declare the serving mode of each model: `api`, `self-hosted`, or `tee`. |
| VSLA-F-14 | L2 | The harness digest and the sandbox image digest MUST be measured (hashed at load, not copied from a manifest) and logged as leaf 0 of the transcript. When a provider publishes a signed weight attestation for a self-hosted model, the MBOM MUST carry it and the weight digest MUST match it. |
| VSLA-F-15 | L3 | Weights, harness, policy and the reproduction sandbox MUST be served from an attested environment: a hardware TEE whose quote the statement carries, or a two-operator split with a 2-of-2 signing group whose two co-signers are **distinct** pinned roots. The quote MUST bind the enclave key, the harness digest, every weight digest and the sandbox digest (see [provenance](provenance.md#environment-and-quote) for how each environment type binds them). An API-served model cannot be measured, so any `serving: api` model caps the Environment pillar at L2. The `signed-quote` type is a reference and test form; a production verifier MUST NOT allowlist a `signed-quote` measurement. |
| VSLA-F-16 | L3 | An L3 statement carries two signatures: the finder's pinned key (I1/E2, the identity the ledger is attached to) and the **enclave co-signature** under a key generated inside the attested environment that MUST NOT be exportable. The quote MUST bind that public key, which the statement carries as `environment.enclaveKey`; a verifier derives it from the verified quote and never pins it (I5). A statement signed by the finder key alone verifies no higher than L2; a statement cannot carry the enclave co-signature unless it was produced inside the measured run. |
| VSLA-F-17 | L3 | Every model in the MBOM MUST carry a provider-signed weight attestation whose digest equals the MBOM digest, and the statement SHOULD carry the digest of a base-model integrity scan when one is published. Attestation proves which bytes ran; it proves nothing about their behaviour. |

## Platform requirements

| Id | Level | Requirement |
|---|---|---|
| VSLA-P-1 | L1 | The platform MUST verify every statement it receives per [verification](verification.md) and MUST record the claimed level, each check's result and kind (external or structural), and the verified level, in a tamper-evident audit log. |
| VSLA-P-2 | L1 | The platform MUST reject a statement whose signature, subject, Merkle root or reproduction fields fail verification, and MUST treat the accompanying report as L0. |
| VSLA-P-3 | L2 | On receipt the platform MUST countersign a [receipt](provenance.md#receipt-the-platform-countersignature) (`{statementDigest, channel, receivedAt, reexecution}`) in a DSSE envelope with the receipt payload type and return it to the finder. A receipt MUST be issued even when re-execution was not attempted, with `status: not-attempted`, so the finder always holds proof of receipt. |
| VSLA-P-4 | L2 | The platform MUST re-execute the reproduction (and, on the Patch track, the three patch executions) in a sandbox it controls, **at the revision named in `subject[1]`**, MUST classify the result with its own classifier (never the finder's flag), MUST check that the test imported or covered the package the platform's **own configuration** names for the repository (`touchedSubject`; never a package name taken from the report, which the finder wrote), and MUST put the result, the sandbox backend, isolation class and digest, the method behind `touchedSubject` (`imported` or `covered`), and the attempt count in the receipt. `touchedSubject` rejects a test that never loads the subject; it does not prove the test exercised the vulnerable path, and a platform MUST NOT describe it as more. Re-execution status is one of `matched`, `mismatched`, `environment-error`, `timeout`, `not-attempted`. |
| VSLA-P-5 | L2 | The platform MUST publish its key, its disclosure policy (embargo, SLOs, trust floors, retention period, isolation class used for re-execution, the countersigners it pins) and its ledger endpoint, so finders know the rules before they submit. |
| VSLA-P-6 | L2 | When a case closes, the platform MUST obtain (or itself provide, when it is the maintainer's authoritative agent) a countersignature on the outcome and MUST hand it to the finder for appending, with `track` equal to the statement's track and **no sequence number** (the finder's operator owns the order; see P-14). `claimed` and `verified` MUST be present only when the platform re-executed (status `matched` or `mismatched`); a deferred or failed re-execution is not an over-claim. Outcomes are `accepted`, `duplicate`, `rejected`, `false-positive`, `reproduced-unresolved`, `withdrawn`, `non-authoritative-release`, `retracted`, `ledger-fork`. Every negative or disqualifying outcome MUST carry a `reason` that is auditable (a model's verdict is recorded with its rationale or its digest, never a boilerplate string). A `false-positive` MUST rest on the platform's re-execution of the **finder's** reproduction at the subject revision having run and not failed by assertion; a failure of the platform's own agents, or a re-execution that was not attempted, timed out or hit an environment error, is `reproduced-unresolved` or no entry. |
| VSLA-P-15 | L2 | `accepted` MUST mean the maintainer, or the platform acting as the maintainer's authoritative agent, accepted the disclosure's outcome (the fix merged, the advisory issued). A finding the platform reproduced but did not resolve is `reproduced-unresolved`, which is neutral. A patch reverted for cause after merge is `retracted`, which is disqualifying, and a platform MAY retroactively re-rate past entries with a signed reason. |
| VSLA-P-7 | L2 | The platform MUST rate-limit and MUST be able to revoke per finder identity (not only per bearer token), and MUST lower a finder's verified level (never below L1 if L1 holds) rather than silently dropping it when the ledger floor is not met. |
| VSLA-P-8 | L3 | The platform MUST verify the environment quote against the vendor's (or the two-operator scheme's) root of trust, MUST check the measurement against its allowlist, and MUST compare every bound weight digest with the MBOM and its provider attestation before granting L3. |
| VSLA-P-9 | all | The platform MUST NOT raise a verified level above what it checked, and MUST NOT present a claimed level as verified in any interface. |
| VSLA-P-10 | L2 (Patch) | The platform MUST run its own adversarial review of a submitted patch, with a reviewer whose model family differs from every patcher named in the MBOM, over the diff and the test output only, and MUST record the verdict digest and `distinctFamily` in the receipt. A finder-asserted review never satisfies E8. |
| VSLA-P-11 | L2 | Re-execution MUST run with no network egress, no access to the platform's signing keys, token issuer, database or other cases, an ephemeral filesystem, CPU, memory, process and time caps, and under a principal distinct from the platform process. A production intake MUST use `vm` isolation; `container` and `process` isolation are development conveniences and MUST be named as such in the receipt and the policy. Signing keys SHOULD live in a separate process or hardware token so that a sandbox escape yields no key. |
| VSLA-P-12 | L1 | The platform MUST bound re-execution admission per identity and globally (queue depth, concurrent sandboxes, CPU budget) and MUST be able to defer or refuse re-execution for an unknown identity (one whose submission presents no **non-neutral** outcome entry that verifies under a countersigner the platform pins; a free `duplicate` makes nobody known) without dropping the report (route it to the slow lane, issue a `not-attempted` receipt). Deferring unknown identities SHOULD be the default. |
| VSLA-P-13 | L2 | Until a case is public the platform MUST NOT expose its status, severity, lane, timestamps, event timeline, test path, command, files touched, diff, agent outputs, audit entries, advisory draft, postmortem, or ledger entries that name it, to any party other than the finder that submitted it and the maintainer; **every** read surface is gated, not only the status summary. Ledger entries for open cases SHOULD be published only after the case is public. |
| VSLA-P-14 | L2 | The platform MUST store, per `(finder key, track)`, the root and count of the ledger it was **shown**, and the entries it countersigned for that finder and track. On the next submission it MUST check that the new ledger extends what it was shown (the root over the first *count* entries equals the stored root) and that every entry it countersigned is **included** in the presented ledger, by canonical bytes and at any position; a changed prefix or an omitted entry is `ledger-fork`. A platform MUST NOT require its entry at a particular position, so that concurrent closes at several platforms never fork an honest finder. State is keyed by the finder's key, never by a reporter name. |
| VSLA-P-16 | L2 | A platform SHOULD anchor each receipt in a transparency log and carry the anchor in the receipt, so that receipt time does not rest on one platform's clock. The anchor's `log-inclusion` form (a signed checkpoint plus an inclusion proof, the shape Rekor and SCITT provide) is what "anchored in a transparency log" means; the `signed-timestamp` form (a pinned log key's timestamp over the receipt digest) proves existence by a time and nothing more, and a verifier MUST accept it for a required anchor only by explicit policy. For a level claim that will be presented to another platform, the anchor is REQUIRED, and a third-party verifier MUST run with `require_anchor`, under which an unanchored receipt fails I3 and is not read for Evidence. |

## Verifier requirements

| Id | Requirement |
|---|---|
| VSLA-V-1 | A verifier MUST use pinned keys (finder, platform, maintainer, provider, environment root, operator, log) obtained out of band, never keys carried in the statement. The one exception is the enclave key, which is derived from a verified quote. A receipt counts only under the pinned `platform:` key that `channel.intakeKey` names; a signature under any other pinned key, including the finder's, is not a receipt. |
| VSLA-V-2 | A verifier MUST compute the level as the minimum across pillars of the highest level whose checks all passed, and MUST report which check failed first on each pillar, and whether each check was external or structural. |
| VSLA-V-3 | A verifier MUST treat a missing or malformed input (a non-canonical payload, a lone surrogate, an unparsable date) as a failed check for the level that input serves, not as an error, and MUST NOT substitute a self-reported value (a history summary, a finder-set flag) for the input. |
| VSLA-V-4 | A verifier SHOULD re-execute the reproduction itself when it has the code and a sandbox, and MUST NOT grant L2 on the Evidence pillar without someone other than the finder having done so at the subject revision. |
| VSLA-V-5 | A verifier MUST count toward `n` and `m` only outcome entries whose countersignature verifies under a key it has pinned (its *countersigner allowlist*), whose `finder` is the statement's finder key or a predecessor in its successor chain, and whose `track` is the statement's track, and MUST verify each entry's signature. The rubric window is by countersigned `at`, never by presented order. `m` counts distinct operators (the name part of the keyid), so two keys of one operator are one countersigner. Two countersigners is a floor on distinct pinned operators, not on independence; the allowlist is the verifier's own judgement. |
| VSLA-V-6 | A verifier MUST hold *expectations* obtained independently of the statement: harness digests per harness name and version, and for L3 an allowlist of acceptable (environment type, measurement, harness digest) triples. Without an expectation the Environment pillar cannot pass an external check above L1. |
| VSLA-V-7 | A verifier MUST judge every time-dependent check at one evaluation instant, `t_eval`: the anchor's `integratedTime` when the receipt's anchor verifies, else the receipt's `receivedAt`, else the verifier's own clock; never a time the checked party wrote. Finder- and platform-key validity windows, `revoke` entries and the rubric's recency decay are evaluated at `t_eval`, so a verification is a function of its inputs and the same anchored statement verifies identically today and later. A verifier MUST enforce the chain `startedAt <= finishedAt <= receivedAt <= integratedTime <= now + skew`. |
